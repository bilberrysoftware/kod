# Methods

This page describes the internal workings of kod.

## Helm chart processing

If you create a package from a Helm Chart, we start by looking at the root helm chart. We copy its source - which
could be a remote URL or local folder - to a local temporary folder and unpack it for processing. This allows us to
introspect the Chart.yaml and values.yaml for subchart dependencies and container image references, respectively.

Currently only the values.yaml file is used to determine container image references. This may change in future
as we may choose to run helm template to discover content. See 'container image search' below for information
on how we search for container images.

Note: kod obeys your system's `TMPDIR` or `TEMP` OS-dependent temporary folder environment variable for this,
so if you want to use a different location, override the appropriate variable before launching kod.

## Helm hints file

A hints file is generated by `kod package` that summarises the package chart and all of the values file elements
that will need to be replaced during a deployment. We do this at package time rather than deploy to ensure the behaviour
is consistent at `kod deploy` time, and so container discovery can be evaluated before any deployment.

Currently, these hints files are generated entirely by kod. In v0.6.0 we will allow you to provide your own hints files
for situations when kod doesn't detect container images correctly (A rare event since v0.2.0).

## Helm values file overriding at packaging time

It's quite common for organisations to fetch external container images and scan them, and then want to perform
offline deployments using these approved images. To avoid the need for you to edit the Helm chart's values.yaml,
we allow you to provide one or more values files at packaging time using the `-f MYVALUES.yaml` flag. Just repeat this
flag multiple times for multiple values files. These will be associated with the chart and will inform
the container discovery and download process. They are also stored for deployment time under 
`MYPACKAGEFOLDER/charts/MYCHART-values-00x.yaml` where x is a monotonic integer count reflecting the order you 
provided the values flags to the kod command.

Note that this behaviour means you don't need a Hints file if kod can detect the image references in the chart
but you don't want to use the default chart versions. Just use the `-f` flag instead.

## Helm values file overriding at deployment time

The following values files are used when running `kod deploy`:-

- First, we apply any package-time overrides you provided via `kod package -f`, if any. These are named `MYPACKAGEFOLDER/charts/MYCHART-values-00x.yaml`
- Next, we apply the kod generated `MYPACKAGEFOLDER/charts/CHART-values.yaml` file, which is generated when the containers are copied to your local registry by `kod deploy`
  - This must be second in case you overrode the source container image reference values using `kod package -f`, E.g. to point to an internal approved source container registry
- Next, we apply any overrides you just provided to `kod deploy -f`, if any.

The above behaviour allows you to differentiate your deployments with different runtime settings so you don't need
a package per deployment, but with the convenience that any standard custom settings can be provided at package time,
and the container image references are always overridden to wherever `kod deploy -r REGISTRY -j PROJECTFOLDER` 
specified they should be copied.

## Helm chart dependency processing

The default `cd MYCHARTFOLDER; helm dependency update` command populates `MYCHARTFOLDERS/charts` with the version
of the dependency in Chart.yaml's `depencencies` element. This is automatically done when creating a package
from an OCI repository's OCI URL - kod doesn't interfere with this behaviour.

In case multiple chart dependencies refer to the same chart version, we relocate these chart folders from
`MYPACKAGE/charts/CHARTNAME/charts/DEPENDENCYNAME` to `MYPACKAGE/charts/DEPENDENCYNAME-DEPENDENCYVERSION`
and leave a symbolic link behind. This ensures we don't fetch the same chart version multiple times.
It does mean, however, you may end up with multiple versions of dependencies. This is down to your chart
maintainer to fix. You can use `kod unpack` and modify the symlinks yourself before a deployment if you wish to,
for example, point all uses of a helm chart to the same version.

## Container image search

We search for container images in the following ways:-

- Look for defaults from `helm create`:-
  - i.e. a top level element in `values.yaml` called `image`
    - Only if it has a required `repository` field and optional registry, tag, and digest fields
- Multiple-container patterns based on `helm create`:-
  - i.e. search for any property in `values.yaml` at all depths that matches a regular expression of `.*[iImage$`
    - Only if it has a required `repository` field and optional registry, tag, and digest fields
- We then continue to package with a warning, rather than failing outright, so you can fix yourself later with a values.yaml file

## Container image version matching

We apply the following logic when looking for container versions:-

- We look for a `tag` element, as described in container image search
- We look for `CONTAINERNAME:TAG` in the `repository` element, as described in container image search
- We fallback to the Chart.yaml's `appVersion` element
- We fallback again to the `latest` tag
- We fallback again to the `master` tag
- We then continue to package with a warning, rather than failing outright, so you can fix yourself later with a values.yaml file

Note that we use `skopeo inspect` to verify each tag first rather than blindly following it to download the image.
